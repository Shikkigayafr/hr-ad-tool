# Панель управления сотрудниками

**СБИС временно отключена до отдельного указания владельца.** Модули и эксперименты сохранены локально в `отложено до API ключа/`, исключены из Git и Docker. `pysaby` удалён из основных зависимостей; рабочие сценарии не вызывают СБИС. Одного `SABY_ENABLED=true` для восстановления недостаточно. Рабочая почта также остаётся выключенной.

![CI](https://github.com/Shikkigayafr/hr-ad-tool/actions/workflows/ci.yml/badge.svg)

Веб-приложение для управления пользователями Active Directory. Позволяет HR-менеджерам создавать учетные записи без прямого доступа к серверу AD.

## 🚀 Реализованный функционал

### Бэкенд (Flask + SQLite)
* **Авторизация и безопасность**: Хеширование паролей, защита от брутфорса (бан на 30 минут после 5 неудачных попыток).
* **Роли (RBAC)**: Админ (видит всё), HR (создает только стажеров своего отдела), Глава отдела.
* **Интеграция с AD**: Настроен модуль `ldap3` (с поддержкой `DRY_RUN` для тестирования без реального сервера).
* **Журнал аудита (Логи)**: Запись всех действий (создание, повышение, удаление) с разграничением видимости по ролям.
* **Экспорт в CSV**: Выгрузка списка сотрудников с корректной кодировкой для Excel.
* **Real-time уведомления**: WebSockets (Socket.IO) для мгновенного обновления ленты событий у всех открытых вкладок.
* **Автоматические бэкапы**: Каждый день в 03:00 создается копия базы данных в папке `backups` (хранится 7 последних версий).

### Фронтенд (Vanilla JS + CSS3)
* **Современный UI**: Темная/светлая тема (с сохранением в localStorage), Glassmorphism, плавные анимации.
* **Адаптивность**: Мобильная версия (таблица превращается в карточки).
* **UX-фишки**: 
  * Скелетоны загрузки (Skeleton UI).
  * Умная валидация форм (сложность пароля, проверка email).
  * Кастомные тосты (всплывающие уведомления) с иконками.
  * Поиск по таблице в реальном времени.
  * Личный кабинет (смена аватара, имени, пароля).
  * Пасхалки (скрытые соцсети разработчика в футере).
  * Красивые страницы ошибок 404 и 500.

### DevOps (Docker)
* **Контейнеризация**: Проект собирается в Docker-образ.
* **Gunicorn + Gevent**: Продакшн-сервер для обработки запросов и WebSockets.
* **Healthcheck**: Docker проверяет доступность приложения каждые 30 секунд.
* **Autoheal**: Автоматический перезапуск контейнера, если он «завис».

### Работа с сотрудниками
* **Отключение вместо удаления:** кнопка «Отключить» блокирует учётку в AD, пишет причину, переносит её в OU `Disabled` и убирает из группы роли. «Вернуть» делает обратное. Окончательно удалить может только админ и только уже отключённого.
* **Массовый импорт из CSV** (`/import`): шаблон, проверка без создания («Проверить»), отчёт по строкам, генерация паролей и скачивание логинов с паролями (пароли показываются один раз).
* **Сброс пароля** из панели: пароль генерируется, в AD включается смена при первом входе.
* **Временные пароли пользователей панели:** созданный админом пользователь обязан сменить пароль при первом входе (до этого доступен только профиль).

## ⚙️ Запуск

Администратор может открыть «Загрузка приложений» и опубликовать MSI или EXE до 300 МБ. MSI добавляется с `/qn /norestart`, параметры EXE указываются в форме. Публикация требует пароля администратора и подтверждения. Панель использует текущую учётку AD для SMB с шифрованием. Пакет копируется в `C:\Deploy` и `SYSVOL/<домен>/scripts`, после чего команда дописывается в `install_all_apps.bat` в SYSVOL. Имена существующих пакетов защищены от перезаписи. Копии батника до изменений сохраняются в `instance/app-upload-backups`. Для этой страницы desktop Compose задаёт `APP_UPLOAD_ENABLED=true`.

### Этот Windows-ПК: автозапуск после входа
Docker Desktop, HR и Kanboard запускаются общим сценарием `F:\docker-autostart\Start-LocalApps.ps1` через `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\LocalDockerApps`. Сначала сценарий ждёт готовности Docker, затем поднимает контейнеры без сборки и скачивания обновлений.
* HR: `http://localhost:5000`; локальная конфигурация `docker-compose.desktop.yml`, существующая SQLite в `instance/hr.db`.
* Kanboard: `http://localhost:8080`; конфигурация и данные в `F:\kanboard`.
* Журнал: `F:\docker-autostart\logs`; инструкция: `F:\docker-autostart\README.md`.
* Обновить HR после изменения кода: `docker compose -f F:\hr-ad-tool\docker-compose.desktop.yml up -d --build --wait`.
Порты опубликованы только на localhost. Конфигурация ниже с PostgreSQL сохранена для отдельного развёртывания; одновременно поднимать обе конфигурации HR нельзя — они используют одно имя контейнера и порт.

### Вариант 1: Docker (PostgreSQL + секреты)
1. Установить Docker Desktop.
2. Создать `.env` из `.env.example` (несекретные настройки: `DRY_RUN`, адрес AD и т.д.).
3. Сгенерировать секреты: `python scripts/init_secrets.py` — создаст папку `secrets/` (в git не попадает).
   Пароли сервисных учёток впишите в `secrets/ad_password.txt`.
4. Запустить: `docker compose up --build -d`. При старте контейнер сам применяет миграции БД.
5. На пустой базе создайте первого администратора: `docker exec -it hr_ad_panel flask --app app init-db`.
6. Откройте [панель](http://localhost:5000/) на компьютере с Docker и войдите как `admin / admin`. Откроется мастер, который попросит адрес контроллера, DNS-имя домена, сервисную учётку и новый пароль администратора.

### Настройка домена при первом входе

- Укажите IP или полное DNS-имя контроллера. Адрес должен присутствовать в его сертификате LDAPS. Для внутреннего CA вставьте PEM-сертификат CA без закрытого ключа. LDAPS использует TCP 636. Если DNS-имя контроллера не разрешается в контейнере, настройте доступ к DNS домена на Docker-хосте.
- Укажите DNS-имя домена и логин сервисной учётки, например `svc_hr@corp.example`. Мастер проверит вход по LDAPS и чтение корня домена. Для операций с сотрудниками сервисной учётке также нужны делегированные права и OU/группы, описанные в [инструкции AD](infra/ad/README.md).
- Задайте новый пароль администратора и нажмите «Проверить и сохранить». После успешной проверки войдите с новым паролем. До завершения мастера начальный администратор имеет доступ только к настройке и выходу.
- Настройки домена сохраняются зашифрованными в томе `domain_setup`, ключ остаётся в `secrets/employee_password_key.txt`. Храните резервные копии тома и ключа отдельно. Повторный `init-db` сохраняет существующие учётки. Если конфигурация AD заранее задана в `.env`, собственный `INITIAL_ADMIN_PASSWORD` позволяет создать первого администратора сразу с этим паролем.

**Переезд со старой SQLite-базы:** положите её в `instance/hr.db` и выполните
`docker compose exec hr-ad-panel python scripts/sqlite_to_postgres.py instance/hr.db`.

### Вариант 2: Локально (для разработки, SQLite)
1. `python -m venv .venv`, `.venv\Scripts\activate`
2. `pip install -r requirements-dev.txt`
3. Создать `.env` (см. `.env.example`)
4. `python scripts/init_secrets.py`, затем задайте в `.env` `SECRET_KEY_FILE=secrets/secret_key.txt` и `EMPLOYEE_PASSWORD_KEY_FILE=secrets/employee_password_key.txt`. Выполните `flask --app app init-db`.
5. `python app.py`

## 🗄️ База данных и миграции
Схема меняется только через миграции (Flask-Migrate / Alembic, папка `migrations/`):
* изменили `models.py` → `flask --app app db migrate -m "что изменилось"` → проверить файл → `flask --app app db upgrade`;
* `flask --app app upgrade-db` — безопасно применяет миграции (и «усыновляет» старую базу, созданную до миграций);
* в Docker это выполняется автоматически при каждом старте.

## 🔐 Секреты
Приложение ищет секрет `NAME` так: файл из `NAME_FILE` → `/run/secrets/name` (Docker secrets) → переменная `NAME` из `.env`.
Через secrets передаются `SECRET_KEY`, `POSTGRES_PASSWORD`, `AD_PASSWORD` (СБИС отложена).

### Безопасность входа и подключений
* Сессия подписана `SECRET_KEY` и привязана к текущему хешу пароля через HMAC. Смена/сброс пароля отзывает остальные браузерные сессии; текущий браузер сохраняется при самостоятельной смене. После обновления старые сессии потребуют повторного входа. Миграция БД не нужна.
* Выход очищает cookie текущего браузера и закрывает его WebSocket-соединения. Для подписанных cookie нет серверного списка отзыва: ранее скопированная cookie остаётся действительной до смены пароля или истечения срока подписи.
* Socket.IO не допускает пользователей с временным паролем. Перед каждой рассылкой проверяются пароль, роль, отдел и наличие учётки; устаревшее соединение отключается. Реализация рассчитана на один worker, как текущий Gunicorn.
* Для рабочего развёртывания настройте HTTPS и `SESSION_COOKIE_SECURE=true`. `TRUST_PROXY=true` допустим только за одним доверенным proxy, без прямого внешнего доступа к приложению. Proxy должен передавать исходный `Host`, перезаписывать `X-Forwarded-Proto` и дописывать адрес TCP-клиента в `X-Forwarded-For`.
* LDAPS всегда проверяет цепочку доверия и имя DC. Для внутреннего CA задайте `AD_CA_CERTS_FILE` и смонтируйте PEM в контейнер; без файла используются системные CA. Непроверенный сертификат больше не принимается. Реальные подключения требуют явно заданных `AD_USER` и `AD_PASSWORD`.
* В production отсутствие `SECRET_KEY` останавливает запуск. Шаблонный ключ из `.env.example` нужно заменить. Явно заданный `NAME_FILE` с отсутствующим/пустым файлом считается ошибкой и не подменяется значением из окружения.
* API и HTML не кэшируются (`Cache-Control: no-store`); добавлены `nosniff` и запрет отображения во frame. CSRF-токен отправляется JavaScript только на свой origin; изменяющие запросы с чужим `Origin` отклоняются.

## 📜 Логи
Каждая строка — JSON (`ts`, `level`, `logger`, `msg`, …): в `docker logs` и в `logs/app.log` (ротация 10 МБ × 5).
* `hrpanel.request` — запросы (метод, путь, статус, время, пользователь, `request_id`);
* `hrpanel.audit` — события: входы, блокировки, создание/удаление/повышение, сброс паролей. Пароли в логи не попадают.
Пример: `docker logs hr_ad_panel | grep '"event": "login_failed"'`.

## 🧪 Тесты
`python -m pytest` — запускает набор из `tests/` (AD имитируется, БД в памяти). Старые отладочные скрипты Saby перенесены в `dont need/`, в тесты и Docker-образ они не входят.

## Архив необязательных файлов
В `dont need/` сохранены разовые эксперименты Saby, устаревший `scripts/create_admin.py` (заменён `flask --app app init-db`), отдельный скрипт настройки Telegram-прокси и локальные резервные копии. Исходные подпапки сохранены; полный список и причины — в `dont need/README.md`. Панель этот архив не импортирует. Для ручного использования скрипт сначала нужно восстановить на исходное место; часть экспериментов меняет данные Saby.

## 🔧 Флаги интеграций (`.env`)
* `DRY_RUN=true` — не подключаться к AD, только имитировать создание.
* `SABY_ENABLED` — временно не включает интеграцию: она вынесена в локальную папку `отложено до API ключа/` до отдельного запроса владельца.
* `AD_SYNC_CHANGES=true` — «Повысить» и «Удалить» меняют ещё и AD (сначала проверить на тестовом стенде).

## 👥 Роли
* **admin** — всё; на странице «Пользователи панели» создаёт HR и руководителей, сбрасывает пароли.
* **hr** — создаёт стажёров/основных и удаляет стажёров только в своём отделе.
* **manager** — видит, повышает и удаляет сотрудников своего отдела.

Сброс пароля сотрудника из панели (кнопка «Пароль») доступен admin и manager, HR — только стажёрам. В AD включается смена при первом входе. Работает при `AD_SYNC_CHANGES=true` (или `DRY_RUN=true`).

В разделе «Данные сотрудников» администратор видит логины AD. Последний пароль, выданный при создании или сбросе через панель, открывается после подтверждения пароля администратора. Для хранения используется Fernet и отдельный ключ `EMPLOYEE_PASSWORD_KEY`, который Compose монтирует из `secrets/employee_password_key.txt`. `scripts/init_secrets.py` создаёт ключ и сохраняет его при повторном запуске. Для запуска без Docker укажите `EMPLOYEE_PASSWORD_KEY_FILE=secrets/employee_password_key.txt`. Храните резервную копию ключа отдельно от БД. При смене пароля вне панели сохранённое значение устаревает. Для ранее созданной записи пароль появится после сброса через панель.

## 📊 Мониторинг
Панель отдаёт **свои** метрики на `/metrics` (Prometheus-формат, защита токеном): запросы и время ответа, входы и блокировки, операции с AD и Saby (успех / отказ / нет связи), сотрудники по отделам и статусам, доступность БД и др. Это дополняет стандартные шаблоны Zabbix (загрузка сервера, диск), а не заменяет их.
* **Zabbix 6.0+:** готовый шаблон `monitoring/zabbix/template_hrpanel_by_http.yaml` (25 элементов, 7 триггеров).
* **Grafana:** `docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d` поднимает Prometheus и Grafana с готовым дашбордом.
Подробности, список метрик и инструкция — в `monitoring/README.md`.

## 🧰 Инфраструктура (`infra/`)
* `infra/inventory/` — скрипты инвентаризации ПК для офиса без домена: запускаются на каждом ПК, пишут по JSON-файлу в общую папку, `Merge-Inventory.ps1` строит сводку (редакции Windows, готовность к Windows 11, железо, программы). Только чтение. См. `infra/inventory/README.md`.
* `infra/ad/` — AD как код: установка леса, OU/группы/сервисная учётка с делегированием прав, GPO. Структура описана в `structure.json`. См. `infra/ad/README.md`. **Сначала лаборатория (`-WhatIf`).**
* `infra/deploy/` — раздача программ при загрузке ПК через GPO (`Install-Software.ps1` + `software.json`, winget/msi/exe).

## ✅ CI
GitHub Actions (`.github/workflows/ci.yml`): тесты на Python 3.11 и 3.12 (SQLite), тесты на PostgreSQL 16, сборка Docker-образа с проверкой `/health` и запуском не от root, проверка `docker-compose.yml`, синтаксис PowerShell-скриптов. Dependabot раз в неделю предлагает обновления зависимостей.

## 📦 Бэкапы
* **Docker (PostgreSQL):** сервис `db-backup` раз в сутки делает `pg_dump` в `backups/hr_*.sql.gz` (7 последних). Восстановление: `gunzip -c backups/hr_....sql.gz | docker compose exec -T db psql -U hrpanel hrpanel`.
* **Локально (SQLite):** копия `instance/hr.db` каждый день в 03:00 (при `FLASK_ENV=production`).
